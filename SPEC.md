# provider-checkmarx Specification

## 1. Purpose and scope

`provider-checkmarx` is a native Crossplane v2 provider that manages Checkmarx One resources as Kubernetes managed resources. It follows the `provider-opencve` architecture: an HTTP client generated with oapi-codegen from vendored Checkmarx One OpenAPI files, and hand-written CRD types and controllers.

| Item | Value |
|---|---|
| Source repository | `github.com/Cliftonz/provider-checkmarx` |
| Go module | `github.com/Cliftonz/provider-checkmarx` |
| Package | `xpkg.upbound.io/cliftonz/provider-checkmarx`, also `ghcr.io/cliftonz/provider-checkmarx` |
| Upbound organization | `cliftonz` |
| API source | per-service OpenAPI files from the Checkmarx One API reference on Stoplight (`https://checkmarx.stoplight.io/docs/checkmarx-one-api-reference-guide`), exported by the human (section 9), vendored in `openapi/` |
| Client | generated by oapi-codegen from the vendored files |
| Crossplane | v2 only |
| Resource scope | Managed resources are namespaced only |
| Capabilities | `SafeStart`; management policies |
| License | Apache-2.0 |

First release, `v0.1.0`: the seven kinds in section 4.2.

Out of scope: cluster-scoped managed resources and Crossplane v1. Out of scope for `v0.1.0`: these Checkmarx One APIs: scans, results, reports, uploads, presets, queries, webhooks, custom states, OAuth clients, users, feedback apps, and the SCA and DAST specific APIs.

## 2. Architecture

The human exports the per-service OpenAPI files from Stoplight (section 9) and vendors them unchanged in `openapi/`. The apis.io mirrored specs and the Checkmarx `ast-cli` source (`github.com/Checkmarx/ast-cli`, `internal/wrappers` and `internal/params/binds.go`) were the secondary sources used to draft this specification; they are not vendored and not used for generation.

Client: only the HTTP client and its models are generated, into one package per service under `internal/clients/<service>/`, each with an `include-operation-ids` allow-list in its own oapi-codegen config naming only the operations a controller calls. Each service has one vendored file and one generated package: `openapi/projects.yaml`, `applications.yaml`, `configuration.yaml`, `access-management.yaml` and `iam-groups.yaml` map to `internal/clients/projects`, `applications`, `configuration`, `accessmanagement` and `iamgroups`, each with its own oapi-codegen config and operation allow-list. Every id field and id path parameter is `format: uuid`, so generated ids are `openapi_types.UUID`. The vendored files are provisional until the Stoplight export lands (section 15).

Connection: `internal/clients.NewClient` returns a `Connection` value, not a generated client type. It holds an authenticated `*http.Client` whose bearer transport performs the token exchange (section 5), plus `BaseURL`, `IAMURL` and `Tenant`. Each kind's controller builds its own generated client from the `Connection`, and the kit's `NewExternal` takes the `Connection`. The generated client is unavailable until the spec export lands, and `Group` talks to the IAM host rather than the API host.

Checkmarx One API shape: management endpoints sit under `{baseUrl}/api/...`, where `baseUrl` is the regional API host (for example `https://ast.checkmarx.net`, with region prefixes such as `eu.`). Identity sits on the regional IAM host (for example `https://iam.checkmarx.net`), with one Keycloak realm per tenant.

HTTP status conventions, for every kind:

| Response | Handling |
|---|---|
| `404` on Observe | the object does not exist |
| `404` on Delete | success |
| `429` | surfaces as an error; no retry inside the provider, the managed reconciler's backoff retries the reconcile |
| any other non-2xx | surfaces as an error carrying the status and the body |

Types and controllers: CRD types under `apis/` are hand-written; controller-gen generates CRDs and deepcopy, angryjet generates managed resource method sets and reference resolvers. Each kind has a hand-written external client in its own controller package, wired through a shared `internal/controller/kit`, as in `provider-opencve`. The kit also carries `Value` (nil-safe dereference), `Time` (time to `metav1.Time`) and `ExternalUUID` (external name parsed as a UUID with a clear error), which every kind uses.

Rejected approaches and their reasons are in `docs/decisions.md`.

## 4. API groups and kinds

### 4.1 Group scheme

One API group per kind, named `<kind>.checkmarx.m.clifton.quest` following the `.m.` convention for namespaced groups. Config kinds (namespaced `ProviderConfig`, `ClusterProviderConfig`, `ProviderConfigUsage`) live in `checkmarx.m.clifton.quest/v1beta1`. Managed resource kinds start at `v1alpha1`.

### 4.2 Resource mapping

| Group | Kind | API | Create | Read | Update | Delete |
|---|---|---|---|---|---|---|
| `project.checkmarx.m.clifton.quest` | `Project` | `/api/projects` | `POST /api/projects` | `GET /api/projects/{id}` | `PUT /api/projects/{id}` | `DELETE /api/projects/{id}` |
| `application.checkmarx.m.clifton.quest` | `Application` | `/api/applications` | `POST /api/applications` | `GET /api/applications/{id}` | `PUT /api/applications/{id}` | `DELETE /api/applications/{id}` |
| `projectconfiguration.checkmarx.m.clifton.quest` | `ProjectConfiguration` | `/api/configuration/project?project-id=` | none; adopts the singleton | `GET` | `PATCH` | no-op |
| `tenantconfiguration.checkmarx.m.clifton.quest` | `TenantConfiguration` | `/api/configuration/tenant` | none; adopts the singleton | `GET` | `PATCH` with an array of `{key, value}`, 204 | no-op |
| `accessassignment.checkmarx.m.clifton.quest` | `AccessAssignment` | `/api/access-management` | `POST /api/access-management`, 201 with the assignment body | `GET /api/access-management/entities-for?resource-id=&resource-type=` | none; a role change is delete then re-create | `DELETE /api/access-management?entity-id=&resource-id=` (provisional) |
| `projectgitsettings.checkmarx.m.clifton.quest` | `ProjectGitSettings` | `/api/projects/{id}/sourceCode/remoteSettings/git` | `POST` | `GET` | `POST` | no-op |
| `group.checkmarx.m.clifton.quest` | `Group` | Keycloak admin API on the IAM host, `/auth/admin/realms/{tenant}/groups` | `POST`, 201, id parsed from the `Location` header | `GET .../{id}` | `PUT .../{id}` | `DELETE .../{id}` |

Fields:

| Kind | `forProvider` | `status.atProvider` |
|---|---|---|
| `Project` | `name` (immutable), `repoUrl`, `mainBranch`, `origin`, `scmRepoId`, `tags` (map), `groups` (group IDs), `criticality` (integer, 1 to 5), `privatePackage` | `id`, `createdAt`, `updatedAt`, `applicationIds` |
| `Application` | `name` (immutable), `description`, `criticality` (integer, 1 to 5), `rules` (list of `{type, value}`), `tags` | `id`, `projectIds`, `rules` (list of `{id, type, value}`), `createdAt`, `updatedAt` |
| `ProjectConfiguration` | `projectId` (immutable), configuration entries `{key, value}` | |
| `TenantConfiguration` | configuration entries `{key, value}`; shape from the ast-cli `TenantConfigurationResponse` | |
| `AccessAssignment` | `entityID`, `entityType` (free string; documented values `group`, `user`), `resourceType` (free string; documented values `tenant`, `application`, `project`) and `resourceID`, all four immutable; `entityRoles` (at least one `{id, name}` role object, `name` at least one character, mutable) | |
| `ProjectGitSettings` | `projectId` (immutable), `url`, `branch`, `privateKey` (`LocalSecretKeySelector`, write-only, never read back) | SHA-256 of the applied `privateKey` |
| `Group` | `name` (at least one character) | `id` |

`name` fields are immutable per field with CEL `self == oldSelf`. Omitted optional `forProvider` fields are late-initialized from the Checkmarx response.

References (generated `*Ref` and `*Selector` fields):

| Kind | Field | Target |
|---|---|---|
| `Project` | `groups` (`groupsRef`, `groupsSelector`) | `Group` |
| `ProjectConfiguration` | `projectId` | `Project` |
| `ProjectGitSettings` | `projectId` (`projectIdRef`, `projectIdSelector`) | `Project` |

### 4.3 Checkmarx behaviors carried into the API

- `Project` delete sends `DELETE /api/projects/{id}`; Checkmarx removes the project's scans and results with it. Keeping a project is done through `managementPolicies`.
- `Application` delete sends `DELETE /api/applications/{id}` even when projects are attached; any refusal by the API surfaces as the error. There is no local check.
- `Project` and `Application` create sends `POST` as given. A duplicate name is rejected by Checkmarx and the API error surfaces in the managed resource's condition; there is no adopt-by-name.
- `ProjectConfiguration` and `TenantConfiguration` compare and patch only the keys listed in `forProvider`; unlisted server keys are ignored and never removed.
- `AccessAssignment` Observe finds the `entities-for` entry whose `entityID` and `entityType` match `forProvider`; none means the assignment does not exist, and roles differing by name is drift, resolved by delete then re-create.
- Any 2xx status counts as success, whatever success code the vendored schema declares, so provisional schemas never reject a real response. A 2xx without the parsed body a call expects (for example a create answering `200` or a read answering `204`) is an error naming the status.
- For `ProjectConfiguration`, `TenantConfiguration` and `ProjectGitSettings`, whose delete is a no-op, Observe reports the resource as not found once `metadata.deletionTimestamp` is set, without calling the API, so the finalizer clears.
- `Project` groups and `AccessAssignment` roles are compared as sets; `Application` rules are compared in order. Empty and omitted collections are the same for `rules`, `tags` and `groups`: empty normalises to nil before comparison and late initialisation, create and update omit empty collections, and clearing any collection is unsupported in v0.1.0.
- `Project` and `Application` drift: a spec field the API response omits is drift on every reconcile and is re-sent; a spec field left unset while the remote has a value is drift unless `LateInitialize` is in the management policies, which is the default.
- `ProjectGitSettings` re-applies the private key once on adoption because the stored hash starts empty; afterwards only a changed hash, `url` or `branch` is drift.
- Admission validations: `AccessAssignment` `entityRoles` has at least one item and each role `name` at least one character; `Group` `name` has at least one character; `Project` and `Application` `criticality` is between 1 and 5.
- `Group` create parses the `Location` header as a URL and takes the base of its path, so a trailing slash or query string still yields the id; a missing header or a non-UUID base is the error above, and a group created but not adopted after a failed parse is resolved by hand.
- A listed configuration key absent from the server is drift and is patched, for both configuration kinds. Configuration entries are a list map keyed by `key`, duplicates are rejected at admission, and at least one entry is required.
- `ProjectConfiguration` and `ProjectGitSettings` require one of `projectId`, `projectIdRef` or `projectIdSelector` by a CEL rule; after adoption the external name stays authoritative.
- Immutable names take part in drift: an external rename is reverted by Update with the spec name.
- `Group` create returns an error naming the `Location` header when the header is missing or its last path segment is not a UUID.
- Sensitive inputs are `LocalSecretKeySelector` references to a Secret in the managed resource's namespace; the SHA-256 of the applied value is kept in `status.atProvider`, and a changed hash is drift (the opencve `Notification` pattern). `ProjectGitSettings` `privateKey` is a sensitive input.

### 4.4 Data sources

None. Observe an existing object with the matching kind and `managementPolicies: ["Observe"]`.

## 5. ProviderConfig and credentials

Config kinds: namespaced `ProviderConfig` (usable in its own namespace), cluster-scoped `ClusterProviderConfig` (usable from any namespace), and `ProviderConfigUsage`, all in `checkmarx.m.clifton.quest/v1beta1`. Managed resources select one with `spec.providerConfigRef: {kind, name}`.

The credentials `source` enum is narrowed to `Secret`. The referenced key holds one JSON document with `baseUrl`, `iamUrl` and `tenant`, plus exactly one of two credential forms; the client picks the grant by which keys are present:

| Form | Keys | Token request |
|---|---|---|
| API key | `apiKey` | `grant_type=refresh_token`, `client_id=ast-app` (or the `azp` claim of the key), `refresh_token=<apiKey>` |
| OAuth client | `clientId`, `clientSecret` | `grant_type=client_credentials`, `client_id`, `client_secret` |

The token request is `POST {iamUrl}/auth/realms/{tenant}/protocol/openid-connect/token`, form-urlencoded. The response carries `access_token` and `expires_in`. Access tokens are cached per credential set and exchanged anew when fewer than 30 seconds of `expires_in` remain or on the next use after a `401`. The bearer transport sends `Authorization: Bearer <access_token>` on every API request; responses follow the status conventions in section 2.

Credential validation fails the connection with one of six credential-document sentinel errors, each with its own test: malformed JSON, missing `baseUrl`, missing `iamUrl`, missing `tenant`, missing credentials, and ambiguous credentials. `apiKey` together with `clientId` or `clientSecret`, even one of them, is ambiguous; `clientId` or `clientSecret` alone without `apiKey` is missing credentials. `baseUrl` and `iamUrl` are trimmed of trailing slashes before the presence check, so `/` is rejected as missing. A seventh sentinel, `ErrMalformedAPIKey`, is returned by `NewClient` for an `apiKey` that is not a JWT with three parts and a base64url JSON payload. An `apiKey` whose `azp` claim is empty is malformed; an absent or null claim falls back to `ast-app`. Credentials are validated before the `ProviderConfigUsage` is tracked.

Cancelling a reconcile cancels its token exchange, and there is no timeout. Reserved characters in the tenant are escaped in the token URL. A token the API rejects with a `401` is evicted whenever the cache still holds it, and the request is retried once when its body can be replayed. Concurrent requests sharing credentials cause one exchange, cached tokens for rotated credentials are dropped once they expire, and a 2xx response without `access_token` fails the request. A missing, zero or negative `expires_in` means the token is used once and never cached.

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: checkmarx-creds
  namespace: team-a
stringData:
  credentials: |
    {"baseUrl": "https://ast.checkmarx.net", "iamUrl": "https://iam.checkmarx.net", "tenant": "my-tenant", "apiKey": "..."}
---
apiVersion: checkmarx.m.clifton.quest/v1beta1
kind: ProviderConfig
metadata:
  name: default
  namespace: team-a
spec:
  credentials:
    source: Secret
    secretRef:
      name: checkmarx-creds
      namespace: team-a
      key: credentials
```

A `ProviderConfig`'s `secretRef.namespace` is required by the CRD schema and always replaced by the resource's own namespace; a `ClusterProviderConfig` uses the namespace as given.

## 6. External name configuration

The external name of `Project` and `Application` is the server UUID. Create sets it from the `id` in the create response; Observe fetches by it. To adopt an existing object, set the `crossplane.io/external-name` annotation to its UUID; with `managementPolicies: ["Observe"]` the provider never changes it.

The other kinds derive their external name from `forProvider` or the create response: `ProjectConfiguration` and `ProjectGitSettings` use the project UUID, `TenantConfiguration` uses the literal `tenant`, `AccessAssignment` uses `<entityID>/<resourceID>`, and `Group` uses the Keycloak group UUID parsed from the `Location` header.

## 7. Build

The `crossplane/build` submodule provides the multi-arch image and `.xpkg` build, lint, and uptest, as in `provider-opencve`. `make generate` regenerates the client, CRDs, deepcopy, method sets and resolvers; `make check-diff` fails when generation leaves a diff. Every source file carries an SPDX header. Commits follow Conventional Commits, scoped by kind (for example `feat(project): ...`). `apis/generate.go` stays identical to opencve (`paths=./...`); on Windows controller-gen writes nothing with that path, so CRDs are generated by CI on Linux and local runs use an explicit package path by hand.

## 8. CI/CD pipelines

All third-party actions are pinned by commit SHA.

| Workflow | Trigger | Outcome |
|---|---|---|
| `ci.yml` | push to `main`, pull_request | lint; check-diff; unit tests; envtest; image and xpkg build; script tests (bats, shellcheck); CRD breaking-change check (crd-breaking-changes) |
| `e2e.yaml` | as in `provider-opencve` | kind e2e, section 11 |
| `e2e-live.yaml` "Live End to End Testing" | push to `main`, `workflow_dispatch`; gated on repository secrets `CHECKMARX_BASE_URL`, `CHECKMARX_IAM_URL`, `CHECKMARX_TENANT` and `CHECKMARX_API_KEY`, skipping with a notice when any is missing | section 11 |
| `publish-provider-package.yml` | push of a `v*` tag | builds from the tag; pushes `xpkg.upbound.io/cliftonz/provider-checkmarx:<tag>` and `ghcr.io/cliftonz/provider-checkmarx:<tag>`; runs `release-check.yml` |
| `release-check.yml` | `workflow_call`, `workflow_dispatch` | the published package installs into kind from `xpkg.upbound.io`, becomes `Healthy`, and the `ProviderConfig` reconciles |

Branch protection on `main` requires: lint, check-diff, unit tests, envtest, build, script tests, and the CRD breaking-change check.

## 9. Upstream tracking automation

None. The Stoplight reference cannot be fetched by tooling, so no workflow can poll it. `spec-tracking.yml` is replaced by a manual spec bump runbook until Checkmarx offers an official download URL:

1. The human exports the per-service OpenAPI files from the Stoplight reference.
2. The files replace their counterparts in `openapi/`, unchanged.
3. `make generate` regenerates the client.
4. The change goes through a pull request; `ci.yml` runs the build, unit tests and the CRD breaking-change check on it.

CRDs are hand-written, so a spec bump normally changes only the generated client; a removed or renamed operation or field the controllers use surfaces as a build or unit test failure on that pull request. A merged spec bump does not release by itself.

## 10. Versioning and release

Versions are semver, starting at `v0.1.0`. While 0.x, a breaking CRD change bumps the minor version. The human pushes the `v<version>` tag on `main`, which triggers `publish-provider-package.yml`; the same string is the git tag and the OCI tag.

## 11. Testing strategy

No live Checkmarx tenant is available.

| Layer | Tool | Scope |
|---|---|---|
| Generation | diff check | Generated client, CRDs, deepcopy, method sets, resolvers |
| Unit | `go test` with `httptest` fakes | One named test per behavior: external clients, both token grants, token caching, the 30-second refresh threshold and the single exchange after a `401`, each HTTP status convention, each credential sentinel error, the malformed `apiKey` rejection, tenant escaping, one exchange under concurrency, cache pruning, the zero `expires_in` case, the panics on an unknown ProviderConfig kind and on factory failure, sensitive input hash drift, singleton adoption and no-op delete |
| CRD validation | envtest | Every CEL rule, including `name` immutability |
| Scripts | bats, shellcheck | `hack/` scripts |
| End to end | kind | Installs the package with placeholder credentials and asserts the `in-use.crossplane.io` finalizer on the default `ProviderConfig`; proves the config controller runs, nothing more |
| Live end to end | `e2e-live.yaml` | Gated on repository secrets being present; runs every example under `examples/namespaced` that lacks the manual-intervention annotation, using API key credentials only |

Controller registration is unit-tested with an unstarted controller-runtime manager pointed at an unreachable address, proving registration through duplicate-name errors, so the `internal/controller` package test passes once per process and CI runs it once.

## 12. One-time setup

Manual steps by the human:

1. Create the empty repository `Cliftonz/provider-checkmarx`.
2. Create Upbound repository `provider-checkmarx` in organization `cliftonz`; store a robot token as `XPKG_ACCESS_ID` and `XPKG_TOKEN`, as in `provider-opencve`.
3. Export the per-service OpenAPI files from Stoplight into `openapi/` (section 9).
4. Publish the first release, `v0.1.0` (section 10).

Scripts under `hack/` and `test/harness/` must be staged with `git add --chmod=+x`, because `core.filemode` is false on the Windows checkout and CI runs them directly.

`package/crossplane.yaml`:

```yaml
apiVersion: meta.pkg.crossplane.io/v1
kind: Provider
```
